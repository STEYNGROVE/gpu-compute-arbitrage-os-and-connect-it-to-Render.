## Transport architecture and threat model

Render's current [private-network documentation](https://render.com/docs/private-network) specifies same workspace/region, optional environment isolation and dynamic internal addressing. Its [PostgreSQL connection documentation](https://render.com/docs/postgresql-creating-connecting) distinguishes internal/external URLs and states that internal self-signed certificates do not support verify-ca/verify-full. Neither document establishes that this application's hostname regex authenticates a server. Sources retrieved during this audit, not inferred from old test results.

Default: require certificate and hostname verification for all remote endpoints, including nonproduction; production loopback also requires TLS. Nonproduction loopback is allowed only for local fixtures/development. TLS `require` and `verify-ca` are deliberately strengthened to full verification. Explicit insecure overrides, global verification bypass, duplicate/unknown parameters, malformed authorities and client certificate/key URL parameters fail closed. No global TLS settings are changed. Explicit `ssl:false` for a permitted fixture/private connection prevents ambient PGSSLMODE from silently altering policy.

Optional private-network exception requires production, Render service marker, `DATABASE_INTERNAL_TRANSPORT=render-private-network`, exact `RENDER_INTERNAL_DB_HOST`, canonical lowercase Render-style single-label hostname and default/5432 port. TLS requests or CA always override the exception. This is operator acceptance of platform network/DNS/environment trust, not cryptographic authentication. Spoofed/rebound private DNS, malicious peers, service compromise or injected configuration remain risks under that exception. No pre-resolution/IP pinning is claimed: private-range checks do not authenticate peers, and provider addresses change. Prefer an existing external endpoint with authenticated TLS if its access policy permits; no endpoint, network policy, certificate or infrastructure was changed.

CA sources: `DATABASE_SSL_CA` or URL `sslrootcert`; conflicting paths fail. The configuration assessment validates policy, not file readability; Pool construction actually reads the CA and fails with a constant identifier. Unexpected hostname case/trailing dots/ports never expand the plaintext exception. Unsupported URL parameters now fail rather than silently overriding policy: deployments using them require review before adoption.

DIRECT_URL goes through the same policy and readiness/schema checks. It remains operator responsibility to establish that primary/fallback identify the same logical database and compatible permissions/schema; no logical-database identity attestation is claimed. One primary and at most one fallback attempt occur per initialize call; no financial workers start through discovery bootstrap failure. Acquisition/query/statement timeouts are each 5 seconds; pool max 15, idle timeout 30 seconds. Total bootstrap/schema checking can take multiple per-query deadlines. Application shutdown has an existing bounded outer deadline; Pool.end itself waits for checked-out clients, so transaction callers must continue releasing clients. No transparent retry of financial writes was added.
